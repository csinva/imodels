AutoOptTree: certifiably optimal decision trees via Autoresearch

Chandan Singh · September 2026

📄 Paper, 🗂 Doc, 📌 Citation

Decision trees are fit greedily in practice: CART and C4.5 pick each split without regard to the splits below it, so the tree they return can be far from the best tree of its size, and there is no way to tell from the output how far. Finding the actual optimum is NP-hard, and the exact solvers that do it (GOSDT, STreeD) spend most of their budget proving optimality rather than finding the tree, which is why they are rarely used. Here we introduce AutoOptTree, an exact solver discovered through autoresearch with frontier agents. It certifies optimality on 63 of 70 benchmark problems against 47 for GOSDT, and is 81× faster on geometric mean. The speedup comes from stronger admissible bounds and from compiling the search, so every tree it returns is still a proven optimum. On a held-out benchmark built from TabArena, which none of the development was done against, the ordering holds: 59 of 70 certified against GOSDT's 43, and 19× faster.

1. Quickstart & example usage

from imodels import AutoOptTreeClassifier
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split

X, y = load_breast_cancer(return_X_y=True, as_frame=True)
X_train, X_test, y_train, y_test = train_test_split(X, y, random_state=42)

model = AutoOptTreeClassifier(regularization=0.05).fit(X_train, y_train)
preds = model.predict(X_test)

There is no max_depth. regularization sets what a leaf costs, in units of misclassification rate, and the model returns the best tree at that price, however deep that turns out to be. A leaf that does not improve the training error by regularization is never worth adding, so the trees stay small on their own.

The fitted model reports whether the search finished, and what it proved:

model.optimal_      # True: no other tree on these features scores better
model.objective_    # 0.1775, the proven minimum of error + 0.05 * leaves
model.n_leaves_     # 2
print(model)        # the tree, as nested if/else on the caller's feature names

At this price a leaf is expensive, and the best tree that exists on breast cancer is a single threshold, which reaches 89.5% on the held-out quarter:

if mean concave points >= 0.05128 then:
    class = 0
else:
    class = 1

optimal_ is the part greedy trees cannot offer. When it is True, the objective reported is a minimum over every tree that exists on the binarized features, not the best of those that happened to be tried. When the time limit is hit first it is False, the model warns, and lowerbound_ and upperbound_ bracket how much could still be left on the table.

What makes a problem expensive is the number of distinct values in the data, not the number of rows: each one is a candidate split. Breast cancer's 30 continuous columns become 11,513 binary features, and the search above certifies in 0.05 seconds only because a leaf priced at 0.05 rules most trees out immediately. Drop regularization to 0.02 and the same problem does not finish in a minute. Discretizing the features first, or pricing leaves higher, is what keeps an exact solver exact in practice.

Each development dataset has a stand-in built from a TabArena classification dataset by a fixed rule, not a choice per dataset: originals largest first, each taking the smallest unused source with enough rows and enough of each class. The stand-in matches the original's rows and features exactly and its class balance to within 0.05, and keeps the features with the most mutual information with the label. Binary originals get binarized features; numeric ones get quantile bins, one bin count per dataset chosen to match the original's number of binary splits. Gray figures are the original's targets. Two stand-ins fall short on splits because a small sample of their source has too few distinct values (chudi, iris), and the two one-feature stand-ins reach 88 to 92% of theirs because the originals are synthetic and have no tied values. TabArena's HELOC and in-vehicle coupon datasets are excluded, since the development suite already contains them. The builder, the manifest and the per-problem results are in agentic-imodels under baselines/benchmarks/external/.

AutoOptTree was produced by the autoresearch loop described in Agentic-imodels (code on github). An agent was given a working exact solver, a fixed benchmark, and a gate that no change may ever return a tree that is not optimal; it proposed bounds, proved them admissible, measured them, and kept the ones that won.

The benchmark is 70 problems: 14 datasets crossed with five values of regularization (0.1, 0.05, 0.02, 0.01, 0.005), each given 30 seconds and 6 GB. Every returned tree's objective is recomputed independently from the tree and the raw data, and checked against the known optimum for that problem, so a solver cannot score by misreporting.

Fig 1 puts every solver the loop produced on one chart, with the baselines, so the whole search is visible rather than only the version that ships. Down is a better tree and left is faster, so the frontier runs along the lower left. Beside it, the key versions and every baseline are run again on TabArena-14, which none of them was developed on.

The right-hand panel is the part that was not developed against. The ordering holds: the shipped model certifies 59 of the 70 held-out problems in 0.0132 ± 0.0007 s against GOSDT's 43 in 0.253 ± 0.014 s, so 16 more problems proved optimal and 19× faster, with the loop's own starting point, pygosdt, at 51 in 0.152 s and STreeD at 46 in 0.633 s. Three runs each, and the spread is small enough that nothing in that ordering is within noise.

Two things the held-out run shows that the development suite did not. GOSDT issues a second false certificate, on the stand-in for chudi at a penalty of 0.005: it reports 0.2518 as optimal where a tree scoring 0.2099 exists, in all three runs. That is independent of the tic-tac-toe case, so the unsound bound is a property of the implementation rather than one unlucky dataset. And STreeD's trees are marginally better on average here, 0.3366 against our 0.3371, while taking 48× as long and certifying 13 fewer problems: on the eleven problems neither solver certifies, STreeD spends its 30 seconds finding slightly better uncertified trees. Being fastest to a proof is not the same as being best without one.

The anytime version holds up too, which is the part worth trusting least in advance: on TabArena-14 its 100 ms budget reaches a criterion of 0.3373, the same as the shipped exact model to four decimals, in 0.0044 ± 0.0000 s against 0.0132 s, while certifying 56.7 of 70 rather than 59. Trading a few proofs for three times the speed survives the move to data the loop never saw, and it puts that point on the held-out frontier.

The stand-ins are also harder than their originals: 59 of 70 certified rather than 63, and the 8-thread version's lead over the single-threaded one narrows to almost nothing (0.0128 against 0.0132 s). GOSDT and gosdt-guesses return no tree at all on 12 to 18 of the held-out problems, stopping at the 6 GB memory budget, which is why their times here are lower than on the development suite while they certify fewer problems.

± is the standard deviation over the three runs. Four of the six solvers certify exactly the same problems every time. The two that move are GOSDT, which certified 46, 47 and 48, and pygosdt, which certified 56, 55 and 55. Only three problems are responsible, and each of them lands within a few seconds of the 30 s cap in every run, so what changes is whether a proof that was always going to be marginal fits inside the budget, not what the solver can prove. AutoOptTree's 63 and its seven unsolved problems are the same in all three runs, and its geometric mean is stable to four decimals across them.

v46 is the loop's last exact version and is not what ships: it uses 8 threads, where the shipped model deliberately uses one. On 8 threads its three largest problems reach the 6 GB memory budget after 13 to 25 seconds and stop there; charged the full 30 s cap instead, its time would be 0.0055 s rather than 0.0054 s. The single-threaded model never approaches that budget, so no other exact row is affected.

The loop also produced anytime versions, which take a fixed time budget per problem and return the best tree found when it runs out, certifying optimality only when the search finishes first. They make up the whole frontier in Fig 1. The best of them takes 100 ms per problem: over three runs it certifies 60.7 of the 70 (61, 61 and 60) in 0.0031 ± 0.0000 s and matches the exact solvers' criterion to four decimals, so half the time of the shipped model for the same trees and two or three fewer proofs. With 1 ms it certifies 46 in 0.0010 s for a criterion 0.6% higher. When a certificate is not needed, that is most of the benefit at a fraction of the time.

The one false certificate is GOSDT's, on tic-tac-toe at regularization=0.02: it reports a tree as optimal whose objective is worse than a tree AutoOptTree certifies. The cause is a scope-conditional lower bound cached unconditionally, confirmed by a two-line patch to the reference implementation. gosdt-guesses in guided mode is a heuristic by design, so it certifies nothing; it is listed to show what the search space costs.

Seven problems are certified by nobody, including AutoOptTree, within the cap: they are the widest continuous datasets, where a column contributes one candidate split per distinct value. No solver in the table certifies them within 600 seconds either.

Accuracy experiments against greedy trees on held-out data are in progress and will be added here: the open question is how much of the optimality gap survives to test time.

3. Methods: AutoOptTree

The objective is the one GOSDT introduced,

minimise   misclassification rate + regularization * (number of leaves)

over every decision tree on the binarized features. The search is a memoised branch-and-bound. The subset of training rows reaching a node (its capture set) is a bitmask over packed 64-bit words, so identical subproblems reached by different paths are recognised and solved once. Each subproblem carries an interval [lb, ub] on its optimal risk and a budget; the search either closes that interval or proves the optimum exceeds the budget, which is what makes the final answer a certificate rather than an incumbent.

Everything that made it faster is a bound, and every bound is admissible: they change which subproblems are visited, never which tree is optimal. The ones that did the most work:

  • Pairwise counts give exact two-leaf values. Counting every pair of candidate splits at a node yields, for each child, the exact loss of its best two-leaf tree. A node whose budget cannot afford four leaves is then solved outright, with no recursion at all.
  • A shape relaxation bounds everything larger. Any tree with four or more leaves has a root split whose two sides have some number of leaves each. Combining the exact one- and two-leaf values with a cheap floor for three-leaf subtrees bounds every such tree at once, so a node can be certified without expanding a single child.
  • The whole search is compiled. Nodes became rows of arrays behind an open-addressing index and the recursion became an explicit stack of frames, so the search and all its stages are one compiled function rather than a Python loop calling compiled kernels. Python re-enters it in short chunks only to enforce the time and memory limits.

One bound that did work earlier no longer earns its place, which is worth recording. Counting triples of candidate splits gives each child its exact best three-leaf and best (2,2)-leaf tree, and while the search was a Python loop that bought enough pruning to pay for its O(m³) cost. Once the search was compiled, the recursion it saved became cheaper than the counting it added, and turning the stage off made the solver faster on every dataset it had ever run on. It is off in the shipped model.

Rows are ordered so that the capture sets of deep nodes occupy few words, which is free because the objective does not depend on the order of the training rows. Together the bounds and the compiled engine account for the speedup: the solver this one started from spent its time proving that subtrees it had already explored could not be beaten, and most of that proving is now done arithmetically from counts the node already has.

A practical note. The compiled search takes about 20 seconds to build the first time it runs on a machine. The result is cached on disk, so every later process loads it in about a second; if the cache directory is unwritable, set OPTTREE_NUMBA_CACHE=0 to skip caching and pay the build each time.

A fuller description of each bound, the ablations, and the ideas that were proved sound but measured to be worthless, is in progress.
